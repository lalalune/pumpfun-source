# Contracts and compatibility evidence

`developer.openapi.json` is the original public specification. Generated TS types live in `packages/backend/src/generated/`. The 67 public developer operations do not cover the website API.

`internal-operations.json` contains 330 strict static operation candidates with provenance; `internal-route-candidates.json` retains broader regex leads and false positives. Neither is a runtime capture or complete API specification. Many operations are privileged, excluded or shared. Do not probe them automatically.

`public-fixtures.json` contains a dated public price response for an explicit local test path (`/services/frontend/sol-price`). It is historical data, not a live quote. Registration accepts GET/HEAD records with a local absolute path, a separate plain query object containing only string values, a final HTTP response status from 200 through 599 (informational responses need a later final response and cannot be standalone fixtures), a non-empty provenance source and an optional plain response-header object containing valid HTTP field names and string values. Invalid records and duplicate canonical method/path/query keys fail before the server is constructed. Fixtures for the built-in `/health`, `/__reconstruction/status` and `/__reconstruction/openapi.json` paths are also rejected, regardless of method casing or query parameters, because Fastify's GET and automatic HEAD handlers make those recorded responses unreachable. Replay preserves valid headers and JSON scalar bodies; duplicate incoming query keys and unmatched requests return 501. This fixture mode does not implement authentication or writes and is not native API compatibility.

Every fixture must explicitly provide `body`; use `null` for a JSON null body. Missing or `undefined` bodies fail registration instead of silently replaying an empty successful response. Fixtures for statuses that cannot carry a body (204, 304) must use a `null` body; any other body fails registration because replay could never deliver it.

Structured JSON fixture bodies (objects, arrays, numbers and booleans) are JSON-encoded even when an explicit non-JSON `Content-Type` is recorded. The recorded media type is retained. Default and JSON media types also encode string and null bodies as JSON; an explicit non-JSON media type preserves raw strings and the existing empty null response. `Buffer` bodies remain raw bytes. These are local replay serialization rules, not an upstream response-format claim.

The backend enforces the documented developer API key requirement on the 67 documented `/v1` operations before fixture replay: a request with no key returns the observed `401 API_KEY_REQUIRED` envelope (`evidence/api-probes.json`), and a key failing the documented `pf_live_` shape (prefix, length, base62 charset) returns `401 API_KEY_INVALID`. The envelope follows the captured response — path without the `/v1` prefix, message naming both key headers — where it differs from the specification's examples; only the timestamp is generated locally. Key checksums, key existence, scopes, revocation and rate limits are not modeled (no key store is observable), and undocumented paths keep the plain 501 fallback. This gate is contract behavior at the harness boundary, not a native operation: the implemented and qualified operation counts stay zero.

`developer-bindings.json` binds all 67 documented developer operations to the captured site's `publicRead` route-contract literals: 18 `content.read`, 17 `graph.read`, 11 `leaderboards.read`, 1 `moderation.read`, 7 `positions.read`, and 13 `profiles.read`. Each entry cites a spec JSON pointer, declared bearer auth and server, the captured object's manifest SHA-256 and exact UTF-16 range, plus every distinct `internal-operations.json` client call site outside the contract definition itself. Empty call-site lists are retained when the inventory has no independent client literal.

The captured contract contains 68 `publicRead` entries. `GET /competitions/{id}/entries/{entryId}/positions` is the sole entry absent from OpenAPI 0.294.0; it remains under `observedNotDeclared` and outside the 67-operation denominator. `scripts/verify-bindings.py` reconstructs that inventory from the captured bytes, checks route-specific `emits` together with `KEYED_ROUTE_CODES`, and verifies provenance, offsets, scopes, auth, call sites, coverage, and unqualified status under normal Python and `-O`/`-OO`.

Contract-bound does not mean implemented or qualified. Website call origins remain unresolved, native compatibility remains 0/67, the broader internal candidate denominator remains unreviewed, and no network request or feature-milestone credit is involved.

`routes.json` defines product scope; `coverage.json` records implementation status. Native API operations and visual/behavior-qualified frontend routes remain zero.
