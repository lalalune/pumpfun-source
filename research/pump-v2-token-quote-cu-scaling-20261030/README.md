# Pump Main token-quote v2 trades: compute-unit scaling, original vs rebuild (2026-10-30)

## Question

This is the token-quote counterpart of `pump-trade-cu-scaling-20261030`,
which covers native SOL. On a token-quote curve, does the rebuild's CU follow
the original's when one operand is swept? And does the v2 CU difference stay
on the creator-fee branch?

Quote mints tested:

- a Token-2022 mint with a TransferFeeConfig (100 bps by default);
- an SPL Token mint.

Operands swept:

- the token amount (10^0..10^14);
- the stub fee bps (protocol and creator branch each on or off);
- the Token-2022 transfer-fee bps (0 / 1 / 100 / 9999).

Earlier token-quote packets (`pump-v2-token-quote-transfer-fee-boundaries`,
`-curve-rent-topup`, and the post-fee/fee-routing drafts) measure
single-point boundaries. None of them sweeps an operand or splits the CU
difference by branch.

## Setup

- LiteSVM (solders 0.27.1), with LiteSVM's builtin SPL Token, Token-2022 and
  ATA programs. Pump runs under the upgradeable loader. The CU limit is set
  with SetComputeUnitLimit, as in the earlier token-quote packets.
- The pump_fees slot holds a 9-instruction SBPFv0 stub generated by
  `producer.py`. It returns the case's fee bps and is identical for both
  images.
- Synthetic IDL-layout state, fixed keys and clock, one fresh VM per case.
  The full state is in `runtime/plan.json.gz`.

## Result

**37 cases, all successes. 0 behavior mismatches.** Error, events, inner
instructions, after-state and tx bytes are equal on every case. CU is equal
on 6/37 cases. The other 31 differ only in their `consumed` log line.

### 1. Amount sweeps: same slope on both images

| series | cases | CU original | CU rebuild | orig - rebuild |
|---|---:|---|---|---|
| buy_v2, T22 quote, 10^0..10^14 | 8 | 118,928 .. 124,579 | 118,930 .. 124,581 | -2 on all 8 |
| sell_v2, T22 quote, 10^0..10^14 | 8 | 97,002 .. 121,122 | 97,002 .. 121,125 | 0 (10^0..10^4, quote 0), -3 (10^6..10^14) |
| buy_v2, SPL quote, 10^0..10^14 | 4 | 157,883 .. 166,775 | 157,885 .. 166,777 | -2 on all 4 |
| sell_v2, SPL quote, 10^0..10^14 | 4 | 125,807 .. 163,345 | 125,807 .. 163,348 | 0 (10^0), -3 (others) |
| buy_v2, T22 transfer-fee bps 0/1/100/9999 | 4 | 122,414 .. 124,520 | 122,416 .. 124,522 | -2 on all 4 |

Within each series, both images move by the same amounts. The differences
are constant offsets, not slopes. Two examples:

- Turning the Token-2022 transfer fee on (0 -> 1 bps) costs +2,106 CU on
  both images (122,414 -> 124,520).
- A sell whose quote rounds to 0 (10^0..10^4 tokens) skips the payouts:
  4 inner instructions instead of 8-9.

### 2. The v2 difference follows the creator-fee branch on token quotes too

| case (10^9 tokens) | protocol / creator fee | buy_v2 T22 | sell_v2 T22 | buy_v2 SPL |
|---|---|---:|---:|---:|
| fees (0, 0, 0) | 0 / 0 | +1 | 0 | +1 |
| fees (0, 95, 0) | 266 / 0 | +1 | 0 | +1 |
| fees (0, 0, 30) | 0 / 84 | -2 | -3 | -2 |

The values are orig - rebuild in CU (orig/rebuild: buy_v2 T22 106,005/106,004,
116,620/116,619, 113,877/113,879; sell_v2 T22 102,599/102,599,
113,214/113,214, 110,507/110,510; buy_v2 SPL 138,003/138,002,
155,327/155,326, 149,364/149,366).

- Turning on only the creator fee moves orig - rebuild by -3 on every quote
  type, the same as on native SOL in `pump-trade-cu-scaling-20261030`.
- The protocol fee and buyback split do not move it.
- buy_v2 keeps a separate +1 when fees are off.
- So the creator-payment path of the v2 handlers (`buy_v2.rs:507`/`1001`,
  `sell_v2.rs:391`) carries the remaining 3 CU for native, SPL and Token-2022
  quotes alike. The exact instructions were not isolated.

## Reproduce

```
python3 producer.py --root <repo> --images '{"original": "<repo>/evidence/original/pump/deployed.so", "candidate": "<candidate.so>"}' --out <dir>
python3 verify.py --images '{"original": "<deployed.so>", "candidate": "<candidate.so>"}'
```

`producer.py` reads only `evidence/upstream/pump.json`, to check
discriminators and account counts. Two runs give byte-identical runtime
files. `verify.py` uses only this folder and the two images. It checks the
image sha256 values, replays all 37 cases on both images, compares every
receipt byte for byte and recomputes the summary. It exits 0 on success.
